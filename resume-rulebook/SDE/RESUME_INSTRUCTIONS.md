# Software Development Engineer (SDE) — resume instructions

Read [shared rules](../SHARED_RESUME_RULES.md), [candidate evidence](../CANDIDATE_EVIDENCE.md), and [keyword matrix](../KEYWORD_MASTER_REFERENCE.md) first. Research accessed 22 October 2026. Resume-writing, ordering and interview suggestions below are general professional guidance derived from the cited work scopes; they are not claims about every recruiter or interview.

Research cohort: [J01](https://www.amazon.jobs/en-gb/jobs/10454438/software-dev-engineer-i-amazon-university-talent-acquisition), [J02](https://www.heizen.work/careers/software-engineer), [J03](https://jobs.lever.co/hevodata/6cbbe304-e065-4711-bf3e-756795d2bc2a), [J04](https://careers.jio.com/frmjobdescription.aspx?JBTITLE=gWTG74MfkJuQf63qpCNAqw%3D%3D&funcCode=am1AraTXtX4%2FW%2FEJK6dzzw%3D%3D&jbID=BJK5KQQgKnRtYB1AKswtAQ%3D%3D), [J32](https://jobs.lever.co/safe/91e23536-2a94-496c-9c74-9dbfd815923f), [J33](https://www.amazon.jobs/en/jobs/10511883/software-development-engineer-i-iesp-merchant-tech). See [methodology](../RESEARCH_METHODOLOGY.md) for small-sample and eligibility limits. Cross-role comparisons may cite other register IDs.

## 1. Role and routing

Target SDE I, SDE-1, Software Development Engineer and new-graduate engineering roles. Use this version when the body emphasizes problem decomposition, implementation judgment and general engineering breadth. Titles overlap: route UI-heavy SDE postings to Frontend, server-heavy ones to Backend, mobile ones to Mobile, and complete application workflows to Full Stack. Use Software Developer for balanced delivery-focused postings.

## 2. Early-career expectations

Expect bounded feature work, readable implementations, debugging and learning from experienced engineers. J03 explicitly asks for DSA/OOP; J01 places algorithms among preferences; J04 focuses on lifecycle and SQL. Do not turn SDE into a universal competitive-programming requirement. J32 is a more demanding 1–3 year comparator, not the six-month baseline.

## 3. Keyword priorities

Core practical emphasis: a demonstrated programming language, problem-solving through implementation, feature delivery and collaboration (J01–J04, J33). Important: DSA/OOP/design principles, testing/debugging, SQL and Git where the JD asks (J03/J04). Optional: domain mathematics, distributed-system exposure and cloud tooling (J01/J32). Conditional: every skill must pass the evidence gate; coursework is labeled coursework. Avoid expert system design, invented coding-problem totals and unsupported scale. These are tailoring priorities; exact frequency-based labels for all 15 categories are in the SDE column of the master reference.

## 4. Required versus preferred

Check each posting's qualification section. J01 restricts graduation to 2026 and treats prior internships as preferred. J03 asks for language proficiency and DSA/OOP. J33 requires 1+ non-internship professional years; 6+ months does not satisfy it. Do not copy a preferred distributed-systems phrase as an established candidate capability.

## 5. Technical skills order

Languages the candidate can defend → CS coursework/fundamentals → strongest implementation stack → databases/APIs → Git and other demonstrated tools. Java may lead for Java-oriented jobs, but do not add C++ without corroboration. Avoid a long framework inventory that displaces implementation evidence.

## 6. Resume sections and fixed layout

Preserve the current template, headings, section order, fonts, margins and all spacing. The user alone makes layout changes manually. Emphasize implementation judgment, accurate CS coursework and relevant verified achievements within the current sections. Make graduation eligibility easy to find through the existing content fields. Keep exactly one page by editing and selecting content, not by changing formatting. Compile and verify page count and absence of overflow before delivery.

## 7. Project selection

Lead with TaleCrafter when an attributable server/data decision is relevant; otherwise ExpressU can demonstrate state, integration and error-handling decisions. Use a second project only if it adds a different engineering challenge. A project feature list alone is not algorithmic evidence. Confirm ownership of any deeper mechanism from the analyses before claiming it.

## 8. Bullet structures

Use a natural length for the contribution: combine related implementation details and outcomes, split unrelated material, and avoid repetitive openings or endings. Examples are not length targets or mandatory sentence patterns.

Use problem/change → bounded implementation → actual result, or contribution → engineering workflow. The examples below are rewrites of existing resume claims, not newly verified work. They demonstrate delivery evidence; they do not pretend to supply missing algorithmic achievements.

```resume-example
Implemented frontend modules from design specifications with designers and backend engineers at Sofmen Technologies.
```

```resume-example
Resolved functional defects and refined application interfaces through stakeholder feedback during development.
```

## 9. Expected responsibilities and outcomes

Show a concrete implementation, a diagnosed defect, a reviewed change or an explainable tradeoff. J03 supports smaller integration tasks under mentorship, which fits early tenure better than architecture ownership. A meaningful functional outcome is enough when no measurement exists.

## 10. Claims requiring extra evidence

Concurrency, fault tolerance, distributed architecture, optimization mathematics, cloud operations and performance gains need specific attributable work. Do not infer these from a provider SDK, database service or an employer's scale.

## 11. ATS wording

Use Data Structures and Algorithms (DSA), Object-Oriented Programming (OOP), problem solving, software development lifecycle, testing and debugging where true. Preserve the actual employment title; use the target title only as positioning, not as a retroactive job title.

## 12. Summary guidance

Use one or two sentences focused on SDE responsibilities and supported core skills, such as DSA/OOP foundations, feature development, API integration, debugging and team delivery. Tailor to the actual JD when supplied. For a general, language-agnostic SDE role, keep language and framework names in skills and project evidence rather than the summary. Do not include an experience month count in the summary, per user preference. Avoid expert, highly experienced and an unsupported list of CS disciplines.

## 13. Professional experience

Keep Sofmen implementation, designer/backend collaboration, defect fixes and Git/GitLab visible. Treat these as engineering workflow evidence. Do not rewrite frontend employment as backend systems development. Add a concrete problem-solving example only after checking the exact work.

## 14. Interview signals

General professional guidance: be ready to explain one algorithm/data-structure choice if claimed, complexity at an appropriate level, one bug investigation and one project tradeoff. J03 supports the DSA emphasis; it does not establish every SDE employer's interview format.

## 15. Final resume checklist

Confirm the current formatting and section order are unchanged, and the rendered resume is exactly one page with no clipping or overflow. Confirm years and graduation eligibility; one defensible language; precise coursework status; at least one substantive implementation example; accurate work/project distinction; current links; natural bullet lengths with clear, non-repetitive detail; all metrics preserved with scope.

## 16. Repetition and weak-claim checklist

Do two bullets merely say built a feature? Does the summary repeat the skills list? Is problem solving only an adjective? Have database use and API calls been inflated into system design? Remove duplicate stack lists and unsupported numerical claims. Keep one distinct contribution per bullet.
