# Backend Developer / Backend Engineer — resume instructions

Read [shared rules](../SHARED_RESUME_RULES.md), [candidate evidence](../CANDIDATE_EVIDENCE.md), and [keyword matrix](../KEYWORD_MASTER_REFERENCE.md) first. Research accessed 22 October 2026. Resume-writing, ordering and interview suggestions below are general professional guidance derived from the cited work scopes; they are not claims about every recruiter or interview.

Research cohort: [J03](https://jobs.lever.co/hevodata/6cbbe304-e065-4711-bf3e-756795d2bc2a), [J08](https://advancesensing.com/pages/careers/careers/software-engineer.html), [J15](https://shipthis.freshteam.com/jobs/P3OR_G1LPfuk), [J16](https://www.pacefin.in/careers/sof), [J17](https://www.wolvion.com/careers), [J18](https://www.squareupdigital.com/careers), [J32](https://jobs.lever.co/safe/91e23536-2a94-496c-9c74-9dbfd815923f). See [methodology](../RESEARCH_METHODOLOGY.md) for small-sample and eligibility limits. Cross-role comparisons may cite other register IDs.

## 1. Role and routing

Target Junior Backend Developer, Backend Engineer, server-side Software Engineer and SDE I postings centered on services and data. Use this version for actual server implementation. Unlike Full Stack it need not prove UI ownership; unlike Frontend/Mobile it cannot rely on consuming APIs. Software Developer is broader delivery, while SDE may prioritize more general reasoning.

## 2. Early-career expectations

J03 describes small integration components under mentorship; J15 asks for at least a year of Python/Mongo despite a 0–2 header. J16 adds Python/Django and production support. J32 is a demanding 1–3 year comparison. Backend entry requirements vary substantially by employer.

## 3. Keyword priorities

Core practical emphasis: a server language, API work, debugging and maintainable services (J03/J08/J15–J18). Important: database/SQL concepts, testing, error handling and collaboration. Optional: cloud, queues, caching and container tooling only for relevant jobs. Conditional: auth, data modeling, concurrency and reliability require proof. Avoid distributed-system expertise, Kafka or Kubernetes from mere exposure. The BE master-matrix column covers all 15 categories and exact coded counts.

## 4. Required versus preferred

J15 requires Python/MongoDB, REST and Git; FastAPI is appreciated. J16 requires Python/Django/PostgreSQL and treats Redis/WebSockets as extras. J03 accepts Java/TypeScript/Python foundations. Existing Node/Express project evidence supports matching Node opportunities; it cannot satisfy unrelated framework requirements by keyword substitution.

## 5. Technical skills order

Server language/runtime → Express.js or another verified server framework → PostgreSQL/SQL/Drizzle → API/auth concepts → Git and personally used test/debug tools. Keep frontend frameworks brief. MongoDB/Mongoose need a concrete project example before prominent use.

## 6. Resume sections and fixed layout

Preserve the current template, headings, section order, fonts, margins and all spacing. The user alone makes layout changes manually. Keep Sofmen frontend work accurate and concise; prioritize attributable server-side TaleCrafter evidence within the existing Projects section without moving it above Experience. Keep exactly one page by editing and selecting content, not by changing formatting. Compile and verify page count and absence of overflow before delivery.

## 7. Project selection

TaleCrafter is the strongest documented server candidate. Prioritize an attributable auth/access-control or persistence workflow before AI branding. Treat advanced transactions, payment verification and integration tests as topics for verification until authorship is established. ExpressU/SafetyBriefer are clients, not backend projects.

## 8. Bullet structures

Use a natural length for the contribution: combine related implementation details and outcomes, split unrelated material, and avoid repetitive openings or endings. Examples are not length targets or mandatory sentence patterns.

Use server capability → concrete control → supported user workflow. If server authorship is unresolved, use supported project claims or retain a client-integration bullet explicitly under its mobile project; never repurpose that bullet as backend implementation. The first example is TaleCrafter; the second is explicitly ExpressU client work.

```resume-example
Integrated Neon Auth and Razorpay subscriptions with backend ownership checks and subscription access controls.
```

```resume-example
Integrated authentication, profile and group APIs with TanStack Query caching and native Keychain token storage.
```

## 9. Expected responsibilities and outcomes

Show what endpoint or service does, how data is stored or protected, and what failure case was handled, when supported. J03/J15 support integration/debugging. Do not claim that a database-backed prototype demonstrates production scale.

## 10. Claims requiring extra evidence

Schema ownership, query optimization, migrations, transaction isolation, queue workers, rate limiting, idempotency, security testing and operational uptime need changes/tests or user confirmation. Client-side role navigation is not server-side authorization.

## 11. ATS wording

Server-side development, backend services, RESTful API development, SQL, data modeling, authentication and authorization should be used precisely. CRUD does not automatically imply transaction design; using managed Neon Auth does not mean building an identity provider.

## 12. Summary guidance

Describe the candidate as an early-career software engineer with personal Node/Express/PostgreSQL project work and professional frontend delivery. Do not claim 6+ months of backend employment. Mention one defensible server contribution rather than expert scalability.

## 13. Professional experience

Sofmen demonstrates team development, requirements, defect fixes and backend collaboration. Preserve that value without changing its scope. Do not move personal project backend work into the Sofmen entry to make the experience appear more relevant.

## 14. Interview signals

General professional guidance: explain request validation, auth versus authorization, schema relationships, error responses and a test strategy for a claimed endpoint. Use project analyses to identify gaps, not as scripts for claiming unperformed work.

## 15. Final resume checklist

Confirm the current formatting and section order are unchanged, and the rendered resume is exactly one page with no clipping or overflow. One attributable server contribution; explicit personal-project context; precise database and API terminology; honest tenure; client-only work labeled; no unverified infrastructure claims; all bullets reviewed for clarity, repetition and preserved outcomes.

## 16. Repetition and weak-claim checklist

Are API, auth and database bullets three descriptions of one endpoint? Does every bullet only say built backend? Remove duplicated stack mentions. Replace unsupported reliable/scalable with a real mechanism, or omit the adjective without inventing a mechanism.
