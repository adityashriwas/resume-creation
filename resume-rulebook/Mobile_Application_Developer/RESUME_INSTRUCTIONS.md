## 1. Role and routing

Target Junior React Native Developer, Mobile Application Developer and cross-platform Mobile Software Engineer. Native Android/iOS and Flutter are separate tracks requiring their own evidence. Choose Frontend for browser UI, Full Stack for actual mobile-plus-server work, Backend for services, SDE for broader engineering and Software Developer for general implementation roles.

## 2. Early-career expectations

J24–J29 cover React Native, Flutter and native platforms, not one interchangeable stack. Junior work includes screens, integration, bugs and review. J28 requires professional Android years; React Native tenure should not automatically be counted as Kotlin development experience.

## 3. Keyword priorities

Core practical emphasis: mobile features, the appropriate platform/framework and collaboration (J13/J14/J24–J30). Important: API integration, debugging, Git, app state/navigation and device-aware behavior. Optional: release tooling, native bridges, push and offline mechanisms by role. Conditional: specific platform expertise, shipping and performance claims require evidence. Avoid generic all-platform proficiency, complete offline support or store-release ownership. See MOB column for the measured priorities across all 15 categories.

## 4. Required versus preferred

J24 accepts Flutter, RN or native alternatives; J25 requires RN fundamentals and personal projects but treats Firebase/navigation tools as extras. J13 explicitly requires WatermelonDB; J28 needs Kotlin/Android lifecycle; J29 needs Swift or Objective-C. RN/Expo experience does not meet these specific requirements automatically.

## 5. Technical skills order

TypeScript/JavaScript → React Native/Expo → React Navigation or Expo Router by project → Query/Zustand → REST/Axios, secure storage and Firebase → Git/GitLab and actual device/build tools. Keep backend and browser stacks secondary unless requested.

## 6. Resume sections and fixed layout

Preserve the current template, headings, section order, fonts, margins and all spacing. The user alone makes layout changes manually. Emphasize Sofmen mobile delivery and relevant ExpressU/SafetyBriefer contributions within the existing sections; use TaleCrafter only when relevant and space permits. Keep exactly one page by editing and selecting content, not by changing formatting. Compile and verify page count and absence of overflow before delivery.

## 7. Project selection

ExpressU offers reported frontend implementation, navigation, caregiver workflows and integrations. SafetyBriefer adds Expo/domain-hook work but only claim attributable optimizations or features. Confirm whether these are professional/client projects before categorizing them. Do not repeat both projects' state stacks without distinct contributions.

## 8. Bullet structures

Use a natural length for the contribution: combine related implementation details and outcomes, split unrelated material, and avoid repetitive openings or endings. Examples are not length targets or mandatory sentence patterns.

Use mobile user task → screen/navigation or integration contribution → functional behavior. The following are existing ExpressU resume claims offered as examples of related mobile contributions. Firebase integration does not imply proven delivery in all app lifecycle states.

```resume-example
Implemented React Native interfaces for caregiver communication with role-based navigation and group administration.
```

```resume-example
Built paginated signal timelines with acknowledgements and WebSocket updates, integrating Firebase notifications.
```

## 9. Expected responsibilities and outcomes

Show navigation, request/state handling, bug fixes and platform-aware behavior only where performed. User benefit may be enabling caregiver communication rather than a fabricated engagement gain. Permission handling, push lifecycle and release debugging are separate responsibilities needing separate evidence.

## 10. Claims requiring extra evidence

App Store/Play releases, Swift/Kotlin modules, offline sync, crash-free rates, device coverage, frame-rate gains and notification reliability need proof. Project analyses note incomplete notification/deep-link behavior and no complete offline queue; do not claim comprehensive implementations.

## 11. ATS wording

React Native, Expo, mobile UI, navigation, state management, REST API integration and push notifications are useful precise terms. Cross-platform refers to shared implementation, not verified parity on every device. Distinguish platform permission handling from backend authorization.

## 12. Summary guidance

Lead with Junior Software Engineer and 6+ months of React Native mobile frontend work. Mention one supported interface/integration strength. Avoid claiming native Android/iOS engineering mastery or multiple published apps without release evidence.

## 13. Professional experience

Use Sofmen's Mobile Application Development context explicitly. Emphasize design implementation, backend/designer collaboration, feedback and Git/GitLab. Exact feature ownership, device testing and deployment responsibilities should be confirmed before detailed bullets.

## 14. Interview signals

General professional guidance: explain navigation/auth gates, server state versus local state, async cleanup and one mobile bug. For claimed notifications explain foreground/background behavior; for secure storage explain client limits. Do not claim release or native-module knowledge based solely on repository configuration.

## 15. Final resume checklist

Confirm the current formatting and section order are unchanged, and the rendered resume is exactly one page with no clipping or overflow. Framework track matches target; platform scope truthful; personal contributions identified; professional/client project context confirmed; no full offline or delivery guarantees; at least one user workflow; related details grouped coherently with natural lengths and readable layout.

## 16. Repetition and weak-claim checklist

Avoid repeating React Native, API integration and state management in every bullet. Distinguish navigation, caregiver communication and timeline behavior. Remove broad production optimization language unless a concrete measured or attributable change supports it.
