# Frontend Developer / Frontend Engineer — resume instructions

Read [shared rules](../SHARED_RESUME_RULES.md), [candidate evidence](../CANDIDATE_EVIDENCE.md), and [keyword matrix](../KEYWORD_MASTER_REFERENCE.md) first. Research accessed 22 October 2026. Resume-writing, ordering and interview suggestions below are general professional guidance derived from the cited work scopes; they are not claims about every recruiter or interview.

Research cohort: [J19](https://www.genyxlabs.com/careers/junior-frontend-engineer), [J20](https://www.narixlabs.com/careers/frontend-engineer-junior), [J21](https://overtminds.com/blog-new/careers/frontend-developer-angular-react/), [J22](https://www.red-sag.com/careers/apply/junior-frontend-developer), [J23](https://www.wolvion.com/careers), [J34](https://unicoconnect.com/careers/frontend-react-developer). See [methodology](../RESEARCH_METHODOLOGY.md) for small-sample and eligibility limits. Cross-role comparisons may cite other register IDs.

## 1. Role and routing

Target Junior Frontend Engineer, Frontend Developer, UI Developer and React Developer for browser interfaces. Use Mobile for React Native/device work, Full Stack for genuine server ownership, Backend for APIs/data, SDE for broad problem-solving and Software Developer for general maintenance. React Native experience is transferable but does not establish browser expertise.

## 2. Early-career expectations

J19/J20 emphasize design implementation, reviewed components and learning; J21 allows strong project exposure. J23 uses semantic HTML and vanilla JavaScript, showing that React is not universal. J34 requires production React/TypeScript for 1–3 years and is a stretch comparison.

## 3. Keyword priorities

Core practical emphasis: JavaScript, UI implementation and relevant framework fundamentals (J19–J23). Important: HTML/CSS, responsiveness, Git, component tests, accessibility and API/state handling where requested. Optional: Next.js rendering modes, design systems, motion and SEO tools. Conditional: browser/device coverage and measured Web Vitals require evidence. Avoid claiming WCAG compliance or design-system ownership from styled components. See FE matrix for all 15 categories and coded prevalence.

## 4. Required versus preferred

J19 wants web basics and a component framework, with React preferred; J20 requires JS/TS and demonstrable React work while Next.js/Tailwind/Figma are nice-to-have. J21 lists accessibility/testing as good-to-have. Do not treat every frontend JD as a requirement for the same state library.

## 5. Technical skills order

JavaScript/TypeScript → HTML/CSS → React/Next.js → relevant styling/state tools → API integration → Git and verified test/browser tools. Keep React Native separate and secondary for web-only jobs. Do not list Angular merely because it is an alternative in a JD.

## 6. Resume sections and fixed layout

Preserve the current template, headings, section order, fonts, margins and all spacing. The user alone makes layout changes manually. Make browser-based TaleCrafter evidence visible within Projects while keeping professional React Native work explicitly labeled. Keep exactly one page by editing and selecting content, not by changing formatting. Compile and verify page count and absence of overflow before delivery.

## 7. Project selection

Use TaleCrafter for a specific creation/library/export UI. Use ExpressU selectively for design translation and state/integration experience, with platform clearly stated. Verify responsive behavior, keyboard navigation, semantic HTML and browser tests before claiming them; neither mobile layouts nor a screenshot proves these.

## 8. Bullet structures

Use a natural length for the contribution: combine related implementation details and outcomes, split unrelated material, and avoid repetitive openings or endings. Examples are not length targets or mandatory sentence patterns.

Use design or user workflow → interface implementation → functional result; or bug/feedback → concrete UI refinement. Examples below are existing professional frontend claims. They intentionally avoid inventing browser-specific accessibility or performance achievements.

```resume-example
Implemented frontend modules from design specifications, working with designers and backend engineers on delivery.
```

```resume-example
Resolved functional defects and refined application interfaces through stakeholder feedback during development.
```

## 9. Expected responsibilities and outcomes

Show design fidelity, reusable components, API-backed UI or feedback-driven refinements where personally performed. J19/J20 connect design implementation with review and tests. Loading/empty/error states are good evidence only when the candidate actually handled them.

## 10. Claims requiring extra evidence

Accessibility compliance, cross-browser testing, Core Web Vitals gains, SEO impact, design systems and frontend architecture ownership require demonstrable work. A Figma handoff does not make the candidate the product designer.

## 11. ATS wording

Frontend/front-end, UI components, responsive design, state management and REST API integration are common terms. Use React for browser code and React Native for native interfaces. TanStack Query manages server state; Zustand is not used in ExpressU.

## 12. Summary guidance

Connect design-to-interface professional delivery with browser project experience. Specify React Native work and React/Next.js project work independently. Avoid pixel-perfect claims unless design comparison was actually performed.

## 13. Professional experience

Sofmen supports design specifications, designer/backend cooperation, bugs and feedback. Preserve the mobile platform context. Do not convert these bullets to HTML/CSS, browser optimization or web accessibility work.

## 14. Interview signals

General professional guidance: explain components/props/state/hooks, asynchronous requests, one rendering decision and one real UI bug. Be ready to distinguish browser and native styling/navigation; show actual behavior rather than only a polished screenshot.

## 15. Final resume checklist

Confirm the current formatting and section order are unchanged, and the rendered resume is exactly one page with no clipping or overflow. Browser evidence visible; mobile context explicit; relevant JS/TS and HTML/CSS supported; UI workflow understandable; no untested accessibility/performance claim; project links work; coherent bullets with natural lengths and readable layout.

## 16. Repetition and weak-claim checklist

Do design translation, responsive screens and reusable components describe the same unsupported feature? Avoid repeating built UI with different verbs. Keep one design, one integration and one defect example only if they add distinct verified contributions.
