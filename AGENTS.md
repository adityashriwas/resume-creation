# Instructions for future resume updates

Whenever the user requests a resume update for a specific role in this project, use the existing `resume-rulebook/` library as the required starting point. Do not tailor from generic resume advice alone.

Current user direction: maintain one consolidated SDE / Software Engineer resume covering the candidate’s broader work and supported skills. Include ExpressU, TaleCrafter AI and E-Learning; omit SafetyBriefer and create-mern-api. Represent maintenance-phase feature implementation in existing applications under professional experience without implying original authorship of those applications. Do not create separate role variants unless explicitly requested again. Emphasize the value of professional contributions without inventing metrics or moving project work into employment. The consolidated version remains a draft pending user confirmation.

1. Read `resume-rulebook/README.md`, `resume-rulebook/SHARED_RESUME_RULES.md`, and the matching role's `RESUME_INSTRUCTIONS.md`:
   - SDE: `resume-rulebook/SDE/`
   - Software Developer / Software Engineer: `resume-rulebook/Software_Developer/`
   - Full Stack: `resume-rulebook/Full_Stack_Developer/`
   - Backend: `resume-rulebook/Backend_Developer/`
   - Frontend: `resume-rulebook/Frontend_Developer/`
   - Mobile Application Developer: `resume-rulebook/Mobile_Application_Developer/`
2. Use the actual target job description, when provided, to resolve overlapping titles and prioritize relevant requirements. For another role, use the closest applicable guide and explicitly adapt it.
3. Review `resume-rulebook/CANDIDATE_EVIDENCE.md`, the current resume, project documentation and relevant available code. Distinguish user-reported contributions, documented capabilities and unverified authorship.
4. Tailor the summary, skills, experience and projects to the target role while preserving truthful responsibilities, genuine metrics and user benefits. Write the summary for the target role and, when supplied, its JD: emphasize supported responsibilities and core competencies rather than a list of languages or frameworks. For language-agnostic roles such as general SDE, keep technology names out of the summary; put them in skills and project evidence. Do not state the experience month count in the summary. Preserve TaleCrafter's user-confirmed real-user usage without inventing an exact count. Never turn personal-project skills into professional experience or mobile API integration into backend ownership.
5. Use content-driven bullet lengths with no fixed character or word limit. Keep related implementation details, context and meaningful outcomes together around one coherent contribution. Split unrelated or overloaded material; do not pad or truncate to make bullets equally long. Use natural sentence structures and avoid repetitive openings, endings and achievements. Avoid repeating project stack names in bullets unless needed to explain a specific mechanism; focus on contributions and user workflows. Review readability, unsupported claims and the rendered document layout.
6. Preserve the current resume template exactly: page size, margins, fonts, font sizes, line and paragraph spacing, section and bullet spacing, indentation, alignment, columns, headings, section order and LaTeX formatting definitions. Preserve existing bold emphasis on retained content and verify that it renders in the PDF. Use hyphen (-) markers for project points. Keep the personal GitHub profile link in the header; omit only project repository GitHub links. Keep contact details on the first header line and the portfolio, LinkedIn and personal GitHub links together on the second line, displaying their full profile paths. Keep ExpressU first in the Projects section for the current SDE resume. Layout and spacing changes belong to the user; edit content only. Use the current `main.tex` formatting as the baseline on each update so the user’s manual changes are respected.
7. Keep the final resume on exactly one page. Fit it by tightening wording, merging related or repeated content and selecting the most relevant supported details, never by changing formatting, shrinking text, clipping content or hiding overflow. Preserve truthful meaning, genuine metrics and essential context in retained claims. Compile the updated resume and verify one page, no overflow and readable text before claiming completion; if rendering is unavailable, explicitly report that page fit is unverified.
8. Deliver the updated resume with a concise review of relevance, evidence and repetition, confirmation of unchanged formatting and verified one-page output, plus any remaining evidence gaps. Character-count reports are not required.
9. Save each successfully compiled and checked final PDF in `final-resumes/<Role>/`, using the same role folder names as `resume-rulebook/`. Name it `Aditya_Shriwas_<Role>_YYYY-MM-DD.pdf` using the user's local date. For a job-specific version, include the company or job identifier in the filename. Preserve previous final versions; use `_v2`, `_v3`, etc. if the filename already exists. Link the saved PDF in the final response. Keep temporary build files in `build/`; do not place drafts or failed/unverified builds in `final-resumes/`.

The library already exists; ordinary resume-update requests do not require rebuilding the entire research library. Refresh the target job description and relevant evidence as needed. Follow subsequent explicit user instructions when they change these preferences.

Use `main.tex` as the editable resume source and `Aditya_Shriwas_Resume.pdf` as the original PDF reference. Project evidence is in `projects/expressu.md`, `projects/talecrafter.md`, and `projects/safetybriefer.md`. The `.vscode/` configuration records the existing Tectonic build setup; intermediate output belongs in `build/` and can be regenerated. Checked final role-specific PDFs belong in `final-resumes/` and should be retained.
