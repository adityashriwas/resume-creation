# Resume workspace instructions

Read `resume-rulebook/README.md`, `resume-rulebook/SHARED_RESUME_RULES.md`, and the matching role guide before tailoring.

- Keep `main.tex` and all tracked examples anonymous, using placeholders for personal information.
- Work on `local/main.tex` for a person's resume. Read their local evidence, preferences, project notes and target job description first. Confirm authorship, metrics and actual technology use with candidate evidence; ask for missing facts.
- Store personal documents, original PDFs, reference resumes and job-specific drafts in ignored `local/`. Share public templates and generic documentation through Git.
- Preserve the user's current formatting and emphasis. Use natural bullet lengths, hyphens for project points, specific contributions and supported outcomes. Give each bullet a distinct purpose.
- Tailor summary, skills, experience and projects to the target role. Separate employment, personal projects and coursework. Use actual job titles and dates.
- Build when requested or authorized. For content-only requests, edit the source and report page fit as unverified. Confirm verified page fit through compilation and inspection of the current output.
- When building, use `local/build/`. Check exactly one page, overflow, readability, emphasis and text extraction. Fit by editing content while preserving fonts and spacing.
- After user confirmation, save approved finals in `local/final-resumes/<Role>/Name_Role_YYYY-MM-DD.pdf`, preserving earlier versions with suffixes. Use the user's local date.
- Before sharing repository changes, inspect `git status` and the staged diff for personal content. Treat previously committed data and Git history as a separate privacy review, since earlier commits retain their original contents.
- Write shared documentation as direct, action-focused instructions: explain what to do, how to do it, and the conditions for proceeding. Preserve the meaning of evidence, privacy and approval requirements when rewording guidance.
